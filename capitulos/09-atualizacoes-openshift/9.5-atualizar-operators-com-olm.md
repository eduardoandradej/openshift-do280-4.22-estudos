## Parte A — Entendendo o conceito

### Política de atualização de operators

Versões novas trazem correções e recursos — e às vezes defeitos e incompatibilidades. O
administrador define uma política com quatro ferramentas:

| Ferramenta | Decide |
|------------|--------|
| **Aprovação** (`Automatic` × `Manual`) | Se o OLM aplica sozinho ou espera aprovação |
| **Canal** | Que sequência de versões o operator segue |
| **Catálogo próprio/espelhado** | Quais versões existem para o cluster (ex.: só as testadas) |
| Forma de instalação | Operators instalados **fora** do OLM (Helm, YAML) não são atualizados por ele nem pela atualização do cluster |

### Canais de operators

Cada fornecedor define seus canais e sua cadência:

- **estabilidade:** `candidate` recebe tudo primeiro; o que se mostra estável vai para
  `stable` (menos novidades, mais confiabilidade);
- **versão maior:** canais como `v1` e `v2` separam mudanças incompatíveis — produção fica
  em `v1` enquanto a homologação testa `v2`;
- nomes variam: Red Hat usa `stable`, `fast`, `candidate` ou `stable-4.22`; operators da
  comunidade, `alpha`, `beta`, `preview`, `latest`...

Trocar de canal (editar a Subscription) **não** atualiza nada por si: só se o canal novo
oferecer versão mais nova **e** a aprovação for automática. Leia a documentação do operator
antes; trocas de canal podem ter efeitos indesejados.

### Onde ver atualizações disponíveis

| Lugar | Mostra |
|-------|--------|
| **Ecosystem › Installed Operators** | "Upgrade available" |
| Subscription (`status`) | `installedCSV` (versão atual), `currentCSV` (mais nova do canal), `installPlanRef`, condição `InstallPlanPending` / razão `RequiresApproval`, `state: UpgradePending` |
| InstallPlan | `spec.approval`, `spec.approved`, `spec.clusterServiceVersionNames` (versão nova), `status.phase: RequiresApproval` |
| `oc get csv` | Versões instaladas |

Aprovar = `spec.approved: true` no **InstallPlan** (não na Subscription). Na console:
**Upgrade available › Preview InstallPlan › Approve**.

### Operators e a atualização do cluster

Um operator pode usar APIs que a próxima versão remove; por isso operators declaram as
versões do OpenShift com que são compatíveis.

> ⚠️ O **CVO bloqueia a atualização do cluster** se houver operator instalado incompatível
> com a versão de destino: `Upgradeable=False`, razão `IncompatibleOperatorsInstalled`.

Ordem correta: **primeiro** atualizar os operators para versões compatíveis com a versão de
destino; **depois** o cluster. Se não houver versão compatível, desinstalar o operator,
atualizar o cluster e reinstalar.

Para "congelar" versões mesmo com aprovação automática, use um **catálogo espelhado** que
contenha só as versões aprovadas.

### Desinstalar

Pela console (**Installed Operators › ⋮ › Uninstall Operator**) ou apagando a Subscription e
o CSV. Recursos do operator podem ficar no cluster: siga a documentação de limpeza.

### OLM v1 (`ClusterExtension`)

A 4.22 traz o **OLM v1** como GA, ao lado do OLM "clássico". Ele é declarativo e usa o
recurso de cluster **`ClusterExtension`** no lugar de Subscription e InstallPlan.

- Na 4.22, OLM v1 é **só pela CLI**: as páginas Installed Operators e Software Catalog não
  mostram seus componentes (use **Import YAML** e **Search**).
- Atualizar = editar a `ClusterExtension` e aplicar (`oc apply`), escolhendo:
  - versão fixa: `spec.source.catalog.version: "1.15.0"`;
  - **faixa** de versões: `version: ">=1.14, <1.16"`;
  - canal: `spec.source.catalog.channels: [stable]`.
- Estado: `status.install.bundle.version` e condição `Installed` com razão `Succeeded`.

```yaml
# trecho de uma ClusterExtension
spec:
  source:
    sourceType: Catalog
    catalog:
      packageName: auditoria-operator
      version: ">=1.14, <1.16"
```

> 📘 **Fonte externa (API `olm.operatorframework.io/v1`, operator-controller v1.12.0):**
> `spec.source.catalog` também aceita `upgradeConstraintPolicy` (`CatalogProvided`, padrão,
> respeita o grafo do fornecedor; `SelfCertified` ignora e permite até rebaixar — perigoso).
> Os campos obrigatórios variam entre versões do OLM v1: confira com
> `oc explain clusterextension.spec` no seu cluster.

## Parte B — Modelo mental e arquitetura

```mermaid
sequenceDiagram
    participant CAT as Catálogo
    participant OLM as OLM
    participant SUB as Subscription
    participant IP as InstallPlan
    participant ADM as Administrador
    participant CVO as CVO
    CAT->>OLM: nova versão no canal
    OLM->>SUB: currentCSV = nova; InstallPlanPending
    OLM->>IP: cria (approved: false se Manual)
    ADM->>IP: oc patch approved=true (ou console: Approve)
    IP->>OLM: instala novo CSV
    Note over OLM: installedCSV = nova
    ADM->>CVO: atualizar cluster
    CVO-->>ADM: Upgradeable=False se operator incompatível
```

## Parte C — Aplicação prática

> Legenda: 🔍 somente leitura · ✏️ altera o cluster
>
> O capítulo não tem exercício prático. Aprovar atualizações de operators no ambiente do
> curso só quando uma atividade pedir.

### 1. Encontrar atualizações pendentes 🔍

```bash
oc get csv -A                                                     # versões instaladas
oc get subscription <s> -n <ns> -o yaml                           # installedCSV × currentCSV, installPlanRef
oc get subscription <s> -n <ns> -o jsonpath='{.status.installedCSV}{" -> "}{.status.currentCSV}{"\n"}'
oc get installplan -n <ns>                                        # APPROVED false
oc get installplan <ip> -n <ns> -o yaml                           # versão nova e fase
```

### 2. Aprovar ✏️

```bash
oc patch installplan <ip> -n <ns> --type merge --patch '{"spec":{"approved":true}}'
oc get csv -n <ns> -w                                             # nova versão Succeeded
```

### 3. Mudar canal ou política ✏️

```bash
oc patch subscription <s> -n <ns> --type merge -p '{"spec":{"channel":"<canal>"}}'
oc patch subscription <s> -n <ns> --type merge -p '{"spec":{"installPlanApproval":"Manual"}}'
```

### 4. Checar compatibilidade antes de atualizar o cluster 🔍

```bash
oc get clusterversion version -o jsonpath='{range .status.conditions[?(@.type=="Upgradeable")]}{.status}{" "}{.reason}{": "}{.message}{"\n"}{end}'
oc adm upgrade                                                     # também mostra condições que bloqueiam
```

### 5. OLM v1 🔍 ✏️

```bash
oc get clusterextension
oc get clusterextension <ce> -o jsonpath='{.status.install.bundle.version}{"\n"}'
oc explain clusterextension.spec.source.catalog
oc apply -f clusterextension.yaml                                  # depois de editar version/channels
```

### Raciocínio operacional e diagnóstico

| Sintoma | Hipótese | Como confirmar | Correção segura |
|---------|----------|----------------|-----------------|
| "Upgrade available" que nunca se aplica | Aprovação manual | `oc get installplan -n <ns>` (APPROVED false) | Aprovar o install plan (após testar) |
| Atualizou sem ninguém aprovar | Aprovação automática | `spec.installPlanApproval` | `Manual` ou catálogo espelhado com versões aprovadas |
| Trocou o canal e nada aconteceu | Sem versão mais nova no canal, ou aprovação manual | `currentCSV`; install plans | Esperado; aprovar se houver plano |
| Atualização do cluster bloqueada: `IncompatibleOperatorsInstalled` | Operator sem suporte à versão de destino | Condição `Upgradeable` do ClusterVersion | Atualizar o operator; ou desinstalar, atualizar o cluster e reinstalar |
| Operator instalado via Helm/YAML desatualizado | Fora do OLM | `oc get csv` não o lista | Atualizar pelo mesmo meio da instalação |
| `ClusterExtension` não aparece na console | OLM v1 só pela CLI na 4.22 | `oc get clusterextension` | Usar CLI, Import YAML, Search |

## Parte D — Relações importantes

| A | B | Diferença essencial |
|---|---|--------------------|
| `installedCSV` | `currentCSV` | Versão instalada × mais nova disponível no canal |
| Subscription | InstallPlan | Onde se escolhe canal/política × onde se **aprova** |
| Trocar canal | Atualizar | Muda as versões visíveis × só ocorre com versão nova + aprovação |
| Atualização de operator | Atualização do cluster | OLM, independente × CVO; operators incompatíveis a bloqueiam |
| OLM clássico | OLM v1 | Subscription/InstallPlan, console × `ClusterExtension`, só CLI na 4.22 |
| Aprovação manual | Catálogo espelhado | Controle caso a caso × controle do que existe para instalar |

## Parte F — Fixação

1. Quem atualiza operators adicionais, e quem atualiza os cluster operators?
2. Em uma Subscription, o que indicam `installedCSV` e `currentCSV`?
3. Onde se aprova uma atualização manual: na Subscription ou no InstallPlan? Como?
4. Trocar o canal de um operator sempre dispara atualização? Explique.
5. O cluster está com `Upgradeable=False` por `IncompatibleOperatorsInstalled`. Que caminhos existem?
6. Como impedir que um operator com aprovação automática receba versões não testadas?
7. Como se atualiza um operator gerenciado pelo OLM v1?

<details>
<summary>Respostas comentadas</summary>

1. O OLM atualiza operators adicionais; o CVO atualiza os cluster operators (com o cluster).
2. Versão instalada e versão mais nova disponível no canal.
3. No InstallPlan, com `spec.approved: true` (`oc patch` ou **Preview InstallPlan › Approve**).
4. Não: só se o canal novo tiver versão mais nova e a aprovação for automática; com manual, um install plan aguarda aprovação.
5. Atualizar o operator para uma versão compatível; se não houver, desinstalá-lo, atualizar o cluster e reinstalar.
6. Com um catálogo espelhado que contenha só as versões aprovadas.
7. Editando a `ClusterExtension` (versão fixa, faixa de versões ou canal em `spec.source.catalog`) e aplicando com `oc apply`.

</details>

## Parte G — Essencial para memorizar

- OLM atualiza operators adicionais; política = aprovação + canal + catálogo.
- `oc get sub <s> -o yaml`: `installedCSV`, `currentCSV`, `installPlanRef`, `InstallPlanPending`.
- Aprovar: `oc patch installplan <ip> --type merge -p '{"spec":{"approved":true}}'`.
- Trocar canal não atualiza sozinho.
- Operators primeiro, cluster depois; `IncompatibleOperatorsInstalled` bloqueia o CVO.
- OLM v1: `ClusterExtension`, só CLI na 4.22; `version` (fixa ou faixa) ou `channels`.
